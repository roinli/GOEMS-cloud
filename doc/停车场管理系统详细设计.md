# 停车场管理系统详细设计

## 1. 项目目标

基于当前 `witos-platform` 多租户版 RuoYi Cloud 框架，规划一套首版停车场管理系统后端方案，满足以下目标：

1. 支持平台级多租户运营。
2. 支持租户管理多个停车场。
3. 支持停车道闸设备直连我方平台，首期先采用模拟设备方式打通流程。
4. 支持车辆入场、计费、H5 缴费、离场放行、超时补费、收入统计、租户提现。
5. 页面暂不开发，先完成后端模块设计、核心业务流程和数据库首版表结构。

## 2. 功能范围

### 2.1 PC 端

1. 登录
2. 仪表盘
3. 停车场管理
4. 停车记录
5. 收入统计
6. 我的账户
7. 提现记录
8. 租户管理
9. 租户套餐

### 2.2 H5 端

1. 扫码进入停车场专属 H5 页面
2. 输入车牌号查询待缴订单
3. 发起支付
4. 支付成功后通知停车平台，触发出场放行

## 3. 角色设计

### 3.1 平台超级管理员

1. 管理租户、租户套餐、停车场基础配置。
2. 查看全部停车场经营数据。
3. 审核和处理租户提现。
4. 查看设备模拟事件和异常记录。

### 3.2 租户管理员

1. 维护本租户名下停车场、通道、设备、收费规则。
2. 查看停车记录、收入统计、账户余额。
3. 发起提现申请。
4. 查看本租户停车场二维码和支付结果。

### 3.3 车主

1. 扫码进入 H5。
2. 查询车牌待缴订单。
3. 在线支付离场费用。

### 3.4 模拟设备

1. 上报车辆入场事件。
2. 上报车辆出场识别事件。
3. 接收平台下发的开闸指令。
4. 回传开闸执行结果。

## 4. 系统定位与模块拆分

## 4.1 总体定位

建议新增独立业务微服务模块 `witos-parking`，而不是继续堆叠到 `witos-system` 中。

原因如下：

1. 停车业务模型独立且表数量较多。
2. 后续会接入真实道闸、支付、结算、设备协议，领域边界清晰。
3. 与系统管理、租户管理、文件服务、定时任务属于协作关系，不适合和 `witos-system` 混写。

## 4.2 建议模块结构

建议在 `witos-modules` 下新增：

```text
witos-modules
└── witos-parking
    ├── controller
    │   ├── admin      // 后台管理接口
    │   ├── h5         // H5 查询与支付接口
    │   └── device     // 模拟设备事件上报与指令回调接口
    ├── domain
    │   ├── base       // 停车场、通道、设备、收费规则
    │   ├── trade      // 停车会话、订单、支付
    │   ├── account    // 账户、流水、提现
    │   └── stats      // 统计汇总
    ├── service
    │   ├── base
    │   ├── trade
    │   ├── account
    │   ├── stats
    │   └── sim        // 模拟设备服务
    ├── mapper
    ├── job            // 日统计、补费检查、账户汇总
    └── integration
        ├── system     // 调用租户、用户、权限相关服务
        ├── file       // 二维码、抓拍图存储
        └── pay        // 支付网关，首版可先留本地模拟
```

## 4.3 与现有模块关系

### `witos-system`

1. 继续承担用户、角色、菜单、部门、租户、租户套餐。
2. 停车场业务通过 `tenant_id` 与租户体系关联。
3. 租户套餐继续使用 `sys_tenant_package`，停车业务只做套餐能力扩展。

### `witos-file`

1. 停车场支付二维码图片存储。
2. 车辆入场/出场抓拍图存储。

### `witos-job`

1. 每日经营统计汇总。
2. 已支付未离场超时补费检查。
3. 账户金额汇总对账。

### `witos-gateway` / `witos-auth`

1. 沿用现有登录与权限体系。
2. 后台接口统一通过网关访问。
3. H5 与设备接口单独放开白名单路径，采用签名或短期令牌校验。

## 5. 核心业务流程设计

## 5.1 停车场开通流程

1. 平台管理员创建租户。
2. 平台管理员为租户分配租户套餐。
3. 平台管理员或租户管理员配置商户结算信息。
4. 租户管理员新增停车场。
5. 配置停车场出入口通道。
6. 绑定模拟设备。
7. 配置收费规则。
8. 生成停车场专属收款二维码。
9. 停车场状态切换为运营中。

## 5.2 车辆入场流程

1. 模拟入口设备识别车牌并调用设备上报接口。
2. 平台按车牌、停车场、入口通道生成一条停车会话。
3. 系统记录入场时间、入口抓拍图、入口设备信息。
4. 如识别到该车存在未完成会话，则标记异常并进入人工处理队列。
5. 平台返回“允许开闸”结果给模拟设备。
6. 设备写入事件日志。

## 5.3 车辆缴费离场流程

1. 车主扫码进入停车场 H5 页面。
2. 输入车牌号查询当前停车场待缴订单。
3. 系统根据收费规则计算应缴金额。
4. 车主发起支付。
5. 支付成功后：
   1. 更新订单为已支付。
   2. 更新停车会话状态为“已支付待离场”。
   3. 写入账户流水。
   4. 向模拟设备下发预开闸授权。
6. 出口设备识别到同车牌时：
   1. 判断是否存在支付有效期内的已支付订单。
   2. 若存在，则放行并完成停车会话。
   3. 若不存在，则重新计算费用，要求补缴。

## 5.4 超时补费流程

1. 订单支付成功后进入离场宽限期。
2. 若车辆在宽限期内离场，订单直接完结。
3. 若车辆超过宽限期未离场：
   1. 原订单标记为已支付但未完成离场。
   2. 系统生成补费订单。
   3. 补费订单金额按“支付后超时段”重新计算。
4. 车主重新支付补费订单后方可离场。

## 5.5 提现流程

1. 租户管理员查看账户余额、可提现余额、冻结金额。
2. 发起提现申请。
3. 系统校验最低提现金额、可提现余额、手续费规则。
4. 申请单进入平台审核。
5. 审核通过后：
   1. 冻结金额转出。
   2. 生成提现出账流水。
   3. 申请单状态改为已打款。
6. 审核拒绝后：
   1. 冻结金额回退可提现余额。
   2. 记录拒绝原因。

## 6.1 运营配置工作流

## 7. 功能详细设计

## 7.1 登录

### 功能说明

沿用现有 `witos-auth` 登录流程，不单独建设停车专属登录。

### 开发设计

1. 停车系统菜单权限挂接到现有权限体系。
2. 平台管理员可查看全部租户数据。
3. 租户管理员默认只允许访问本租户数据。
4. 租户下如果绑定多个停车场，允许基于“当前停车场上下文”切换。

## 7.2 仪表盘

### 功能说明

展示经营总览、今日数据、月度数据、收费趋势。

### 展示指标

1. 今日进场数
2. 今日出场数
3. 当前在场数
4. 今日收入
5. 本月总收入
6. 本月总单数
7. 平均每单
8. 车位周转率
9. 收费趋势图

### 后端设计

1. 实时数据来自 `parking_session`、`parking_order`。
2. 趋势图和月汇总优先使用 `parking_daily_stat`，避免大表实时聚合。
3. 提供按停车场筛选和按日期区间查询。

### 建议接口

1. `GET /parking/dashboard/overview`
2. `GET /parking/dashboard/trend`

## 7.3 停车场管理

### 功能说明

维护停车场、通道、设备、收费规则、停车场支付二维码。

### 后端子功能

1. 停车场列表查询
2. 新增/编辑停车场
3. 配置通道
4. 绑定设备
5. 配置收费规则
6. 生成和下载二维码
7. 启停停车场

### 数据规则

1. 停车场必须归属一个租户。
2. 一个停车场可以有多个入口、多个出口。
3. 通道与设备是一对多关系。
4. 收费规则首版按停车场维度生效，一个停车场同时只有一个启用规则。
5. 停车场删除采用逻辑删除，若存在未完成停车会话则禁止删除。

### 建议接口

1. `GET /parking/admin/lot/list`
2. `POST /parking/admin/lot`
3. `PUT /parking/admin/lot`
4. `GET /parking/admin/lot/{id}`
5. `POST /parking/admin/gate`
6. `POST /parking/admin/device`
7. `POST /parking/admin/rule`
8. `POST /parking/admin/lot/{id}/qrcode/generate`

## 7.4 停车记录

### 功能说明

按订单号、车牌、停车场、状态、支付状态、日期查询停车记录。

### 记录视图建议

一个列表行展示：

1. 订单号
2. 车牌号码
3. 所属租户
4. 停车场
5. 进场时间
6. 出场时间
7. 停车时长
8. 应收费用
9. 支付方式
10. 当前状态

### 后端设计

1. 列表以 `parking_session` 为主体。
2. 金额字段来自当前主订单或最后一笔补费订单。
3. 详情页返回停车会话、订单列表、支付流水、设备事件、抓拍图片。
4. 支持导出。

### 建议接口

1. `GET /parking/admin/session/list`
2. `GET /parking/admin/session/{sessionId}`
3. `GET /parking/admin/session/export`

## 7.5 收入统计

### 功能说明

按日期、租户、停车场汇总进出场次数和总收入。

### 后端设计

1. 使用 `parking_daily_stat` 作为统计主表。
2. 当天数据允许“统计表 + 实时增量”方式补齐。
3. 支持平台维度、租户维度、停车场维度查看。

### 建议接口

1. `GET /parking/admin/stat/daily`
2. `GET /parking/admin/stat/export`

## 7.6 我的账户

### 功能说明

租户查看账户余额、可提现余额、冻结金额、手续费率，并发起提现。

### 后端设计

1. 账户主表使用 `parking_account`。
2. 提现金额校验：
   1. 大于最小提现金额。
   2. 小于等于可提现余额。
   3. 租户状态正常。
3. 手续费按租户结算配置计算。
4. 提交申请后冻结相应金额。

### 建议接口

1. `GET /parking/account/summary`
2. `POST /parking/account/withdraw/apply`
3. `GET /parking/account/withdraw/list`

## 7.7 提现记录

### 功能说明

展示租户提现历史及审核状态。

### 后端设计

1. 主表为 `parking_withdraw_order`。
2. 支持查询处理中、已通过、已拒绝、打款失败。
3. 平台端和租户端共用一套数据，不同角色数据权限不同。

## 7.8 租户管理

### 功能说明

平台管理员维护租户信息，查看租户管理员账号、手机号、邮箱、套餐、租期、账户余额、停车场数量、状态。

### 后端设计

1. 基础租户信息继续使用 `sys_tenant`。
2. 商户结算信息使用 `parking_tenant_settle_config`。
3. 账户余额来自 `parking_account`。
4. 停车场数量通过 `parking_lot` 聚合。

### 设计原则

1. 不把停车账户金额直接冗余写入 `sys_tenant`。
2. 列表页按需联表或走聚合查询 VO。
3. 平台新增租户时同步初始化账户和结算配置。

## 7.9 租户套餐

### 功能说明

在现有租户套餐基础上增加停车业务配额能力。

### 套餐建议扩展字段

1. 最大停车场数量
2. 最大设备数量
3. 是否启用 H5 支付
4. 是否启用提现

### 后端设计

1. 套餐菜单权限仍存 `sys_tenant_package.menu_ids`。
2. 停车业务配额直接扩展 `sys_tenant_package` 字段。
3. 创建/编辑停车场、绑定设备时校验套餐额度。

## 7.10 H5 车牌查询与支付

### 功能说明

车主输入车牌号查询待支付订单，完成支付后通知停车平台。

### 页面最小闭环

1. 停车场二维码识别到 `parking_lot_id`
2. 输入车牌号
3. 查询未完成订单
4. 展示停车时长和应付金额
5. 发起支付
6. 支付成功页提示尽快离场

### 后端设计

1. 仅允许查询当前停车场内的待支付订单。
2. 若同一车牌存在多条未完成记录，以最近一条待支付记录为准。
3. 支付成功后必须写入支付流水和账户流水。
4. 支付成功不直接结束停车会话，必须等待出口事件闭环。

### 建议接口

1. `GET /parking/h5/lot/{lotId}/order/query?plateNo=`
2. `POST /parking/h5/order/{orderNo}/pay`
3. `GET /parking/h5/order/{orderNo}/result`

## 7.11 模拟设备直连

### 目标

在接入真实硬件前，先把设备事件流、平台指令流和异常处理流跑通。

### 模拟范围

1. 入场识别上报
2. 出场识别上报
3. 开闸指令下发
4. 开闸结果回传
5. 心跳上报

### 后端设计

1. 设备上报统一走 `device` 接口。
2. 平台记录原始事件到 `parking_io_event`。
3. 指令下发和执行结果记录到 `parking_gate_command`。
4. 设备接入层保留 `vendor_code`、`device_secret`、`config_json`，为后续真实设备对接留接口。

### 建议接口

1. `POST /parking/device/event/entry`
2. `POST /parking/device/event/exit`
3. `POST /parking/device/event/heartbeat`
4. `POST /parking/device/command/{commandNo}/callback`

## 8. 数据库设计原则

1. 所有业务表统一带 `tenant_id`。
2. 金额字段统一使用 `decimal(10,2)` 或 `decimal(12,2)`。
3. 时间统一使用 `datetime`。
4. 删除采用逻辑删除，关键交易表不做物理删除。
5. 订单号、流水号、指令号使用业务唯一编号，不依赖主键展示。
6. 汇总表与明细表分离。
7. 设备事件与业务订单解耦，原始事件必须可追溯。

## 10. 关键状态设计

## 10.1 停车会话状态

1. `IN_PARK`：停车中
2. `WAIT_PAY`：待支付
3. `PAID_PENDING_EXIT`：已支付待离场
4. `COMPLETED`：已完成
5. `ABNORMAL`：异常

## 10.2 订单状态

1. `UNPAID`
2. `PAID`
3. `CLOSED`
4. `REFUNDED`

## 10.3 提现状态

1. `PENDING`
2. `APPROVED`
3. `REJECTED`
4. `PAID`
5. `FAIL`

## 11. 定时任务设计

## 11.1 每日统计任务

1. 按停车场汇总日收入、进场数、出场数、在场数。
2. 结果写入 `parking_daily_stat`。

## 11.2 超时补费扫描任务

1. 扫描 `PAID_PENDING_EXIT` 会话。
2. 超过宽限期则生成补费订单，并更新会话状态为 `WAIT_PAY`。

## 11.3 账户汇总校验任务

1. 汇总订单收入与账户流水。
2. 校验账户余额是否一致。
3. 异常时写告警日志。

## 12. 接口安全设计

1. 后台接口：沿用登录态 + 菜单权限。
2. H5 接口：二维码携带停车场短期签名参数，避免随意枚举。
3. 设备接口：采用 `device_code + timestamp + sign` 签名校验。
4. 支付回调：验签、幂等、状态前置校验。
5. 开闸指令回调：按 `command_no` 幂等处理。

## 13. 开发顺序建议

## 第一阶段：跑通最小闭环

1. 停车场管理
2. 通道与模拟设备
3. 收费规则
4. 车辆入场
5. H5 查询支付
6. 出口识别放行
7. 停车记录查询

## 第二阶段：运营与结算

1. 仪表盘
2. 收入统计
3. 我的账户
4. 提现申请
5. 平台审核提现

## 第三阶段：增强能力

1. 超时补费
2. 设备心跳与离线监控
3. 异常停车处理
4. 真机设备协议适配层

## 14. 首版边界说明

以下内容建议不纳入第一版开发范围：

1. 月租车/储值车
2. 优惠券、减免券
3. 场内反向寻车
4. 发票能力
5. 多支付渠道并行
6. 实时视频流对接
7. 复杂阶梯计费和节假日计费

## 15. 落地建议

1. 先建设独立 `witos-parking` 模块。
2. 先使用模拟设备接口，把“入场-支付-离场-结算”跑通。
3. 数据模型首版保持稳定，页面可以后置。
4. 后续真实道闸接入时，尽量只替换 `integration` 和 `service.sim` 层，不改交易核心表。
